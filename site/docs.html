Using modest-deploy

Set a server up once, then launch apps with one command, and deploy them on every push.

Before you install

modest-deploy doesn't set up the server. You do that once, and modest-deploy check checks it. Step by step goes through it in detail. On a new Ubuntu 26.04 LTS server you need the list below. 24.04 LTS also works, but it can't stop a compromised app from opening other ports (why).

  • Sign in with an SSH key, added when you make the server, as your own user with sudo. Turn off signing in by password, and as root.
  • A firewall that lets in only SSH (from your own address, if you can), HTTP, and HTTPS. Most providers have one in their control panel.
  • Automatic security updates: apt install unattended-upgrades.
  • Node 26 (24 or later works), and Caddy, from their own package repositories.

Install

terminal
$ sudo npm install -g modest-deploy
$ sudo modest-deploy check
$ sudo modest-deploy install --domain deploy.example.org

Or run it from a clone of the repository, which Node runs as it is: sudo git clone https://github.com/thisismodest/modest-deploy.git /opt/modest-deploy, then sudo ln -s /opt/modest-deploy/src/cli.ts /usr/local/bin/modest-deploy. For launch, install it on your computer too.

check lists what it relies on, each marked ok or with what to fix. install runs it first, and won't go on until everything passes (add --anyway if you're sure). Then it installs the deploy listener, the deploy service, and the nightly backup. Point the deploy domain's DNS at the server (an A record, and AAAA if it has IPv6). That's where GitHub sends its messages.

Launch an app

From your computer, with gh signed in and SSH access to the server:

terminal
$ modest-deploy launch blog blog.example.org --server myserver --template example/template
  1. Makes the repository on GitHub (private, unless you add --public), from your template if you name one. If it's there already, it's used as it is: only the key and webhook below are added.
  2. Adds the app on the server: its own user, folder, keys file, service, and its domain in Caddy, which gets and renews its HTTPS certificate.
  3. Connects them: gives GitHub the server's read-only deploy key, and a webhook for the "Workflow runs" event, signed with a secret made for this app.
  4. Tells you what's left: point the domain's DNS at the server (an A record, and AAAA if it has IPv6), and push.

Without gh, or signed out of it, launch changes nothing: it says how to get it, and prints the same steps to do by hand, with your app's own modest-deploy add command for the server, which prints what to add on GitHub.

Add --redirect www.blog.example.org (or several, separated by commas) for domains that send visitors to the app's own, at the same path. They never reach the app, and no domain can be used by two apps. Run add again on the server to change them.

Each app is given memory of its own: 512M (or all that's left, if less), or what you give with --memory (see Memory).

Memory

Each app's memory is set aside for it alone, and is also its ceiling. The server keeps a quarter of its memory for itself (never under 384M), for the system, SSH, Caddy, the listener, and deploys; apps share the rest, and one is added only if it fits. So however busy apps get, together they can't run the server out of memory, and one can't take another's. An app that goes over its own is restarted, and nothing else is touched.

A server has a little less memory than its size (the kernel keeps some), so these are close, not exact. list gives the real figures.

terminal
$ modest-deploy launch club club.example.org --server clubserver --memory max
$ sudo modest-deploy resize blog --memory 1G

Sizes are whole megabytes or gigabytes (768M, 2G), at least 128M, or max for all that's left. list shows each app's memory and what's given out, and check says if apps have more than the server has for them (after moving to a smaller server, say). After giving the server more memory or cores, run install again: it sizes everything to the server.

Each app's Node thread pool is sized to the server's cores (the cores and two, at most 18). That's what lets modest-auth check a password on each core: on a server with more cores, more people can sign in at once.

Small apps can share a server. Anything with personal data, money, or real traffic is better on a server of its own: list --server shows them all, from your computer.

What an app does

  • Starts with node server.js, and listens on process.env.PORT, at process.env.HOST (127.0.0.1). A version listening anywhere else isn't deployed, so nothing reaches it but through Caddy.
  • Keeps what it writes in process.env.DATA_DIR. Everything else is read-only to it.
  • Answers GET / once it's ready, with anything but a server error.
  • Has a lockfile (package-lock.json) if it has dependencies.
  • Has CI at .github/workflows/ci.yml that runs on pushes to main.

Its keys, such as an email service's, go in /etc/modest-deploy/env/<name>.env, one KEY=value a line, then modest-deploy restart <name>. With modest-auth, name Caddy as the proxy in front: trustedProxies: ["loopback"].

Every push

When CI passes on main, GitHub sends a signed message to the deploy domain. The server:

  1. ignores anything unsigned, or not a successful run of CI for a push to main in the app's own repository;
  2. fetches the repository with the app's own read-only key, and checks GitHub's host key against the ones GitHub publishes;
  3. deploys only if the commit is still the newest on main, so an old message sent again can't roll it back;
  4. refuses a release over 1GB or 200,000 files, or one the disk hasn't room for (it always keeps 1GB free);
  5. builds the release as a separate user, with dependencies exactly as the lockfile says and install scripts off, then makes it owned by root and readable only by the app;
  6. switches to it, restarts the app, and checks it answers within a minute, and only on 127.0.0.1; if not, the version before comes back.

The last three releases are kept. To deploy again by hand: sudo modest-deploy deploy <name>.

Updating

terminal
$ sudo npm install -g modest-deploy@latest
$ sudo modest-deploy install

From a clone, sudo git -C /opt/modest-deploy pull instead of the first line. Running install again rewrites every unit it made, the apps' included, so they use the new version, and restarts those whose unit changed.

Restoring a backup

Stop the app, put the copy back as the app's own, remove SQLite's -wal and -shm files (they belong to the database being replaced), and start it:

terminal
$ sudo systemctl stop modest-deploy-blog
$ sudo install -o md-blog -g md-blog -m 600 /var/backups/modest-deploy/blog/2026-10-25/app.db /var/lib/modest-deploy/blog/app.db
$ sudo rm -f /var/lib/modest-deploy/blog/app.db-wal /var/lib/modest-deploy/blog/app.db-shm
$ sudo systemctl start modest-deploy-blog

Its logjournalctl -u modest-deploy-<name>
The deploys' logjournalctl -u modest-deploy-deploy

Copy /var/backups/modest-deploy off the server too, or turn on your provider's backups.

What it doesn't do

  • Set the server up, as above.
  • Run apps that need more than Node, such as a browser. Those are better in a container of their own.
  • DNS, email, or payments. Those stay with your providers.
  • Run across several servers. An app that outgrows a shared one moves to a server of its own, set up the same way.
